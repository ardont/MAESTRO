# Пополнение знаний из оценённых диалогов

После `USER_FEEDBACK_RESPONSE` support_service сохраняет оценку. Только при
оценке **5** он отправляет POST в MAESTRO `/memory`: ID диалога, исходную
проблему из `Dialogs.problem`, сообщения пользователя и оператора с ролями
и датами, оценку и комментарий. Отправка ожидает ответ API; ошибка HTTP или
индексации пробрасывается в обработчик Kafka, а не выдаётся за успешное сохранение.
Автоматическая повторная доставка зависит от настроек Kafka-потребителя.

MAESTRO повторно проверяет порог оценки, суммаризирует диалог через
`OLLAMA_HOST/api/generate`, модель `OLLAMA_MODEL` (по умолчанию `gpt-oss:20b`).
Извлекаются вопрос и итоговая рекомендация оператора. Неполезные диалоги
(приветствия, шутки, отсутствие решения) получают `status=skipped`, даже с
пятью звёздами. Промпт требует убрать персональные данные и не додумывать
результат; это модельная суммаризация, а не гарантия правильности рекомендации.

Сводка записывается одной точкой в существующую `QDRANT_COLLECTION`
(по умолчанию `data_files`): unnamed dense + sparse `bm25` с IDF, через те же
эмбеддеры и `upsert_chunks_batch`, что использует `index_knowledge_base.py`.
Полный индексатор не запускается, коллекция не пересоздаётся. UUID точки
стабилен для ID диалога: повторная доставка обновит её, а не создаст дубль.
Payload содержит `doc_type=category=support_dialog`, question, solution,
dialog_id, feedback и ссылку на историю support_service. Это опыт поддержки,
не официальная статья. Сырой диалог и комментарий оценки в Qdrant не пишутся.
Снижение оценки после сохранения не удаляет уже добавленное знание.

## Настройка и применение

В support_service:

- `MAESTRO_MEMORY_URL=http://memory-api:8989/memory` — в общей сети
  `rlt_hack_network`; для запуска на хосте `http://localhost:8989/memory`.
- `MAESTRO_MEMORY_TIMEOUT=300` — таймаут запроса, включая Ollama и эмбеддинги.

В MAESTRO (сервис memory-api):

- `OLLAMA_HOST`, `OLLAMA_MODEL` — уже задаются в Compose.
- `MEMORY_OLLAMA_TIMEOUT=180` — ожидание генерации сводки.
- `SUPPORT_SERVICE_URL=http://localhost:8067` — база ссылок на переписку;
  задайте адрес support_service, доступный тому, кто открывает источник.
- Существующие `QDRANT_*`, `EMBEDDING_MODEL_NAME` и доступ к локальной модели.

Compose копирует код в образ: после изменения нужно пересобрать сервисы:

```sh
# В MAESTRO
docker compose up -d --build memory-api
# В support_service
docker compose up -d --build app
```

POST `/memory` принимает `dialog_id` (можно опустить — извлекается из сообщений),
`messages` с `dialog_id`, `text`, `role` (`user`/`support`), `created_at`,
`feedback` (1–5) и необязательный `feedback_text`. Сообщения должны принадлежать
одному диалогу. До 1000 сообщений и 60000 символов сериализованной переписки;
превышение не обрезается молча. Сводка ограничена 250 символами вопроса и 450
символами рекомендации, чтобы одна точка помещалась в компактный chunk.

Ответы: `saved` с `point_id`, `skipped` с причиной; HTTP 422 при некорректных
данных/сводке, 503 при недоступности генерации или индексации. Вызовы индексатора
сериализованы внутри одного worker, блокирующая работа выполняется в thread.
При большом потоке потребуется отдельная очередь; сейчас обработчик оценки
ожидает суммаризацию и индексацию в рамках существующей транзакции.

Проверка без сервисов и загрузки моделей:

```sh
PYTHONPATH=RLT_project .venv/bin/python -m unittest tests.test_dialog_knowledge -v
```

Тесты support_service: `python -m unittest tests.test_dialog_memory -v`
в окружении с его requirements.txt.
